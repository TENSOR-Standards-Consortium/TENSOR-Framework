# Cross-domain investigation examples v1

Three fictional cases use the unchanged Core `0.1.0-draft.1` binding. They span all seven investigation domains. They are additional example definitions and records, not revisions of the working graph, published releases, frozen review package, or schema.

- `soc-signin`: Morgan, session s-42, forwarding rule r-7, company approval, unresolved delivery, scoped response, and handoff. This is the interactive counterpart of the website's five-minute introduction.
- `workload-cloud-egress`: workload identity, cloud object read, independent network observations, ticket scope, unknown content delivery, and a bounded response.
- `attachment-host-tool`: mailbox delivery, independent artifact-byte comparison, process execution, application request, retained unknown-to-supported content revision, separate unknown delivery, and scoped containment approval.

Each bundle includes an exact-byte pinned composed definition. Question IDs retain their public/vendor/company namespace, and optional question metadata records domain and layer ownership/version. Composition keeps transitions within one artifact as required by the existing binding. It does not pretend a cross-layer selection is a route in the separate public graph. Each yes/no/unknown route continues a separately assessed proposition without asserting its answer, causality, or response permission.

The three layers are public example investigation questions, a fictional vendor's product-specific checks, and a fictional company's policy questions. They are authored examples rather than independent implementations or endorsements. Source evidence is fictional and unavailable; observations explicitly describe the assumed discriminators, provenance basis, and gaps. Validator success checks the record and binding, not the truth of those observations. All action records are planned. No queries, evidence retrieval, permission checks, or response actions execute.

Optional `record.metadata.walkthrough` supplies presentation order and exact assessment/decision entry references. It adds no Core requirement. Consumers can ignore it and still inspect the complete record. The website derives routes from actual definition transitions and recorded Decision selections, not adjacency between frames. The content revision is recorded before a transition selects its later assessment; no historical selection is silently rewritten.

Run `node examples/investigations/v1/build.mjs` to regenerate, or add `--check` to verify deterministic bytes. `manifest.json` pins the emitted definitions, bundles, and catalog. `npm run check` includes this verification and positive/negative record tests.
